# 全站第二阶段：性能、实用功能与工程化

## 阶段 1 — 体积与首屏（最高收益）

### 1.1 Rapfi 包去重（省 ~43 MB）

实测：四个包的 `rapfiSource`(39 KB)、`wasmBase64`(1.5 MB)、`dataBase64`(13.4 MB) **SHA-256 完全一致**，仅 `workerSource` 不同。

做法：**保留 `v10ultra/file-package.js` 为唯一引擎包**（不动它的 global，`v10exp.js` 已依赖），其余三个包瘦身为只含自己的 `workerSource`（Flash 另保留 `expert/proof/training/expertWorker`）。三个 wrapper 的 `loadFilePackage()` 在 `file://` 下先加载 `v10ultra/file-package.js`，再加载自己的小包，按 `rapfiSource + workerSource` 顺序拼 Blob（与现有 `v10exp.js` 完全相同的模式）。

同步改：`build-gomoku-v10thinker-file-package.mjs`、`build-gomoku-v10champion-file-package.mjs`、`build-gomoku-v10flash.mjs`。

**"确保没有任何损失"的验收**（全部必须通过才算完成）：
1. `node tools/test-gomoku-training-policy.mjs`（更新断言：引擎字段来自 Ultra 包）
2. `node tools/check-gomoku-page-integration.mjs`（`file://` + HTTP 双协议）
3. `node tools/check-gomoku-experiment-page.mjs`
4. **新增** `tools/test-gomoku-file-package-dedup.mjs`：解码四个包，断言引擎三字段与 Ultra 逐字节相等、各 `workerSource` 等于磁盘文件、Flash 的 expert/proof/training 未丢
5. **补上现有测试盲区**：`check-gomoku-page-integration.mjs` 目前只测 Ultra/Flash/Exp 的 `file://` 运行时，**Thinker 与 Champion 从未做过 file:// 运行时验证**。先补这两项的 `file://` 黑白落子断言，再改包
6. `node tools/run-gomoku-model-pair.mjs` 跑 Ultra↔Thinker、Ultra↔Champion、Ultra↔Flash 换色完整对局，`complete=true`

`v10champion/` 目录下的独立引擎文件（`rapfi-single.js/wasm/data`，10.7 MB）**保留不动**——HTTP worker 直接用它们，AGENTS.md 也声明该目录自包含。

### 1.2 three.js 本地化
下载 `three@0.160.0` UMD 到 `public/vendor/three/three.min.js`，首页改本地引用，保留 CDN 作为 `onerror` 兜底。加入 `VERSIONED` 列表。

### 1.3 i18n 按需加载
拆成 `i18n-dict-zh.js` / `i18n-dict-en.js`，`i18n-dict.js` 变为同步加载器：默认只注入中文包；`ClubI18n.setLang('en')` 时按需注入英文包。存储语言为 `en` 的用户在 boot 时先等英文包加载再 apply。中文用户省 ~120 KB。
同步更新 `test-club-donations-page.mjs` 等直接 `vm.runInContext(i18n-dict.js)` 读 `window.ClubI18nDict` 的测试。

### 1.4 首屏阻塞收敛
- `i18n-dict.js` 与 `member-identity.js` 在剩余 16 个同步页面统一改 `defer`（顺序：字典在前）
- `service-gate.js`：保留早注入的 `visibility:hidden`（防闪现），但把网络超时从 5 s 降到 2.5 s，并优先用 `localStorage` 缓存立即放行
- 不 defer `i18n.js`/`club-common.js`/`service-prompts.js`（页面内联脚本在解析期就调用它们，defer 会破坏顺序）

## 阶段 2 — 数据层（新表 + 新 action）

新增 `supabase/club-notifications-schema.sql`（幂等，`create table if not exists`）：

```sql
club_notifications(id, user_id, kind, title, body, link, dedupe_key, read_at, created_at)
  unique index (user_id, dedupe_key) where dedupe_key <> ''
club_member_profile_settings(user_id PK, show_points bool default true,
  show_donations bool default false, show_games bool default true,
  show_checkin bool default false, headline text <=80, updated_at)
```
两张表都 `enable row level security` + deny-all 策略 + 仅 `service_role` 授权。

`club-drive/index.ts` 新增 action（沿用现有命名与 `getUserAccess` 鉴权）：

| action | 鉴权 | 用途 |
|---|---|---|
| `notifications_list` | 登录 | 最近 50 条 + `unreadCount` |
| `notifications_mark_read` | 登录 | 按 id 或全部已读 |
| `member_profile_public_get` | 登录 | 入参 `memberId`（`club_member_points.id`）；只返回 name/class/points + 按本人开关放行的捐赠合计、游戏战绩、签到与兑换计数；**绝不返回 email/user_id** |
| `member_profile_settings_get` / `_set` | 登录本人 | 读写四项开关 + headline |
| `search_all` | 公开 | 聚合公告/活动/成员/商品/教学资源，服务端限 20 条/类 |

通知生成点：公告或活动发布、报名审核、积分变动、兑换处理、新留言（通知有 `can_messages` 的人）、权限变更。

## 风险与边界

- Rapfi 去重是唯一高风险项：先补 Thinker/Champion 的 `file://` 运行时测试，再改包；任何一项验收失败即回滚到现有四个自包含包。
- 不改任何训练数据、模型权重、`.git`、已有 SQL 迁移；新表只新增文件，不 `drop` 既有表。
- `club-member-profiles-schema.sql` 含 `drop table cascade`，**绝不重跑**。
- 个人主页读取一律走 Edge Function 投影，不放宽 RLS，避免泄露 email/user_id。
