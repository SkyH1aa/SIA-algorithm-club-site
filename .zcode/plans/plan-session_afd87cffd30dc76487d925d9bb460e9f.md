## 背景

社团代理目前只匹配生成接口，Agent 请求 `GET /v1/models` 时在认证前即返回 404 `path`。代理路由也没有自己的模型目录，因此不能可靠地从其他 Chat 模型配置推断可用模型。

## 实施方案

1. **路由配置模型 ID**：在 `public/chat-admin.html`、`public/chat-admin.js` 和 `public/chat-admin-i18n.js` 的路由创建/编辑表单加入“可发现模型 ID”，每行一个；支持编辑现有路由，显示保存结果，提供中英文提示。ID 按上游实际模型名填写，前端和后端均做数量、长度、重复项及非法字符校验。
2. **持久化并兼容现有数据**：在唯一主脚本 `supabase/club-chat-schema.sql` 给 `chat_proxy_routes` 增加幂等字段和受限校验，更新 `chat_proxy_admin` 保存逻辑与 `supabase/functions/chat/index.ts` 请求字段校验。新路由默认空列表；旧管理客户端更新时若未提交该字段，保留原值，避免覆盖。保持版本冲突保护与现有权限。
3. **提供模型列表接口**：在 `supabase/functions/chat-api-proxy/index.ts` 增加 `GET /functions/v1/chat-api-proxy/<route-id>/v1/models` 和对应 CORS 预检，使用现有 `cap_` 密钥、路由启用/撤销检查以及 admission/release 生命周期；仅返回该路由配置的模型 ID，格式兼容 OpenAI 模型列表，如 `{"object":"list","data":[{"id":"...","object":"model","owned_by":"club"}]}`。支持 Bearer 及适用于兼容客户端的 `x-api-key`，同时提供时必须一致。拒绝未授权、已禁用或撤销的访问，不返回上游地址、Secret 或密钥信息，也不调用上游。
4. **保持生成行为不变**：模型列表只是发现信息，不作为生成接口的模型白名单，也不修改模型名称或转换协议。空列表返回合法空结果，明确提示管理员需填写真实上游支持的 ID；现有生成请求的转发、流式响应和安全约束保持不变。
5. **更新交付物**：补充本地 mock、部署说明及相关中英文管理提示；通过现有构建脚本更新 Chat 与代理的 Dashboard 副本及 SQL 副本，按仓库约定更新变更日志和静态资源哈希。只修改工作区，不自动部署或执行数据库变更。

## 验证

- 为真实代理处理器增加路由隔离、正确模型列表、空列表、密钥错误/撤销/路由禁用、CORS、请求方法、租约释放和不访问上游的测试，同时保留原生成端点的字节转发、安全和流式测试。
- 为管理页、后端和 SQL 增加创建、编辑、清空、无效模型 ID、重复项、旧客户端省略字段、版本冲突及中英文切换覆盖；mock 与生产契约保持一致。
- 运行相关 Node、Deno 测试，SQL 使用项目规定的真实 PostgreSQL 解析器校验；检查生成副本、UI tokens、资源版本、训练模型构建与 `git diff --check`。环境缺少依赖或数据库时明确标明未验证，不把模拟通过当成真实部署通过。
- 部署需按 SQL → 相关 Edge Functions → 前端的顺序执行；最后使用 Agent 配置社团代理 Base URL 和路由访问密钥，拉取列表并选择实际模型验证。未经单独授权，不连接或修改线上数据库，也不发起真实上游调用。
