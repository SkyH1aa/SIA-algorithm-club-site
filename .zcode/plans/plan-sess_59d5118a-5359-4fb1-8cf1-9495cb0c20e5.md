## Goal
Replace the assistant’s dependency on provider-native function/tool calling with a model-authored, server-validated query plan, fixed server-side read execution, and a final model answer. Preserve the existing read-only/privacy boundaries and the single-request quota, lease, and audit lifecycle. Do not make paid upstream calls, inspect real API keys, deploy Supabase, or alter production data.

## Implementation
1. **Add a bounded plan contract** in the shared assistant code. The planning model response will be required to contain only a small JSON object with a finite action (`query`, `clarify`, or `answer`) and, for queries, a bounded list of existing read-tool names plus arguments. Define limits on bytes, query count, keys, and property shapes. Reject markdown wrappers, extra keys, malformed JSON, unknown operations, and invalid arguments. Reuse `executeAssistantReadTool()` as the authoritative validator, so accepted plans still cannot specify arbitrary tables, columns, URLs, SQL, RPCs, or writes.
2. **Replace the active native-tool loop with two explicit model stages** in `chat/index.ts`:
   - Planning request: send the existing fixed assistant policy, published supplemental prompt, retrieved static references, user conversation, and a concise read capability catalog as ordinary prompt text. Do not send native tool declarations. Parse and validate the returned plan server-side.
   - Execution: only for a valid `query` plan, invoke the existing bounded read executor serially with the authenticated member JWT. Preserve ambiguity, unavailable/paused/empty status, query bounds, source projection, and current source-card checks. Invalid plans and clarification requests cause zero business reads.
   - Answer request: send the conversation plus the validated plan outcome and bounded query evidence as untrusted data, with explicit instructions not to claim a successful query unless evidence status and rows support it. Disable native tools here too. For `clarify` and `answer`, skip reads and use the final answer stage with the validated outcome.
3. **Keep one accounting envelope for both stages.** Keep one request ID, one `chat_begin_generation`, one lease, and one `finishGeneration`. Rework `assistantToolBudget()` into a two-stage reserve estimate (planning prompt plus bounded final evidence), enforce the context/request/output limits before each dispatch, and aggregate token usage across both model responses. Preserve conservative settlement when usage is missing and guarded refunds only when upstream is demonstrably unstarted. Keep cancellation propagated through both model requests and the read executor. Do not call `callResponses()` twice as a public handler, since it would create separate admissions and audit records.
4. **Reuse protocol adaptation without native tool schemas.** Use the existing `protocolRequest()` and SSE parsing/normalization for Responses, Messages, and Chat Completions. Add a small internal response collector or extend the existing collector to return bounded assistant text and terminal usage for a no-tools response. Validate that the plan response completed and is within limits; never forward planner text, reasoning, or raw provider errors to the browser. Return only the final answer as normalized Responses SSE and preserve current source headers.
5. **Improve safe diagnostics.** Replace the broad `assistant_tools` catch-all for this flow with bounded internal categories such as plan parse/validation failure, query preparation failure, answer-stage failure, and upstream HTTP/network failure. Store only safe category/status metadata; do not log provider response bodies, credentials, plan contents containing user text, or member rows.
6. **Update deployment and behavior documentation.** Replace native-tool compatibility claims with the two-stage plan behavior, clarify the number of model requests and shared accounting, and document validation and failure behavior. Correct the `club-drive` secret instruction: its source reads `CLUB_SERVICE_ROLE_KEY`; do not claim that no additional/ custom secret is needed unless the deployment already has that exact secret configured. Keep deployment instructions manual and state that this work does not deploy anything.
7. **Regenerate the Chat Dashboard bundle** using `node tools/build-chat-dashboard-bundles.mjs`; do not hand-edit generated bundles. `club-drive` needs no code change unless implementation findings prove an interface mismatch; its existing authenticated read action remains the executor boundary.
