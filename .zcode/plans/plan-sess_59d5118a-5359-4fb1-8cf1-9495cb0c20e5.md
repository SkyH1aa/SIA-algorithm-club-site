## 根因
当前榜单按姓名/昵称查询时，固定查询层把名称构造成 `eq."xxx"`；而普通 PostgREST/Supabase `.eq()` 语义应是 `eq.xxx`，双引号可能被当作值的一部分。直接读取前几名没有 `name` 过滤，所以能读到该人；加姓名过滤则返回空或不可用。现有榜单 mock 只无条件返回预设行，未验证过滤后是否真的匹配，因此没有捕捉到问题。

## 实施步骤
1. 在 `supabase/functions/_shared/chat-assistant-tools.ts` 增加独立的精确等值参数构造函数，供 `member_name`、游戏榜单 `name`（nickname/username）使用；仅让 URLSearchParams 负责 URL 编码，不手动增加双引号。保留现有带引号的 `artLiteral`，继续用于公告标题的 POSIX regex `match`，不做全局替换，避免改变不同 PostgREST 操作符的语义。
2. 同步修改 `supabase/functions/club-drive/index.ts` 的独立副本：成员姓名过滤改用无引号等值构造；公告/活动分类状态当前已使用独立枚举构造，保持不变。确保生成的 `club-drive-dashboard-index.ts` 与源文件一致。
3. 强化 `tools/test-chat-assistant-tools.ts`：
   - 更新六个榜单、两种方向、两种排序字段的姓名 URL 断言为 `eq.<name>`；
   - 使用真实的 mock 过滤逻辑，根据 `nickname`/`username` 对 `name` 过滤，分别验证“按前几名可返回”和“按指定姓名仍能返回同一行”；
   - 覆盖中文、逗号、百分号、括号、引号、反斜杠、`&` 等名称字符，确认 URLSearchParams 编码后服务端收到的 decoded 参数仍是精确姓名；
   - 保留公告标题 regex 的带引号断言，防止修复时误伤标题查询。
4. 在 `tools/test-chat-backend.ts` 增加真实 handler mock 回归：先验证五子棋普通榜单的无姓名查询返回前几名，再提交包含明确昵称的 `read_game_leaderboard` 计划，断言 `businessReads` 的 `nickname=eq.<昵称>`、返回行和最终证据均成功。这样覆盖 planner → shared tool → live endpoint → answer 的完整路径，而不仅是 URL 单元测试。必要时增加计划 prompt 的明确要求：用户明确给出游戏昵称时使用 `name` 精确过滤，不能把姓名当作普通文本或忽略。
