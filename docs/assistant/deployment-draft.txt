Assistant administration deployment draft (instructions only)

1. Follow docs/chat-deployment/README.md using the Supabase web Dashboard.
   For a first assistant installation, paste the complete club-chat-schema.sql
   into SQL Editor. For the math/live-read update of an existing current assistant,
   no SQL is needed. Replace the complete chat Edge Function index.ts with the
   generated chat-dashboard-index.ts and the complete club-drive index.ts with
   club-drive-dashboard-index.ts from docs/chat-deployment/, then deploy both.
   club-drive is a full source copy preserving other actions, not a helper patch;
   updating chat alone cannot enable the new member/content query action.
   Publish the updated
   static assets, including chat-math.js and all local KaTeX fonts/CSS/JS/LICENSE,
   through the site's existing publishing process.
   No PowerShell, Supabase CLI or build commands are required for deployment.
   This file executes no deployment.
2. Sign in to public/chat-admin.html using the existing dynamic super-admin roster.
   Existing assistant data loads automatically after authorization. Open Assistant
   knowledge to inspect it. Refresh remains available for failures or conflicts.
3. Select an enabled, nondeleted model visible to all users, backed by an enabled,
   nondeleted provider. The frontend filters admin_get; the backend authorizes it.
   Saving enabled=false immediately disables runtime availability. Other saved
   model/welcome/suggestion/instruction edits enter the next published snapshot.
4. Review docs/assistant/source-manifest.json and current public pages. Pick seed.json,
   review the safe text preview, then explicitly submit JSON import. This saves drafts
   without publishing. The seed excludes exact ECA times/attendance requirements
   because the static join-page statement is not current-schedule confirmation;
   account, event, points and shop records are never part of this seed.
5. Click “填入小Bru预设” if you want the reviewed Bru identity, welcome and
   suggestions. It fills only those fields, never the model/enabled state. Review
   and explicitly save the configuration. system-prompt.txt is the copyable prompt;
   config-preset.json is for reference, NOT the knowledge JSON import.
   Save/review configuration and draft changes. On version conflict, writes stop
   without automatic retry. Refresh, compare current values and preserved drafts,
   and intentionally resubmit. Archived drafts can be restored by saving/importing
   the same slug and count toward total corpus limits.
6. Explicitly Publish after verifying saved model and active documents. Publication
   creates an immutable snapshot. Rollback submits the current version and an
   existing release ID; it changes only the active release pointer, keeping drafts.
   The historical model still has to be enabled and public for rollback/runtime.
7. Verify assistant login/binding, source links, quota, separate local history,
   attachments, language/theme behavior and disable/rollback after deployment.
   For live reads check published announcements/events, name-and-points privacy,
   all six independent boards and query timestamp/status/limits. Semantic tools
   choose filters, database asc/desc and bounded pages: page 1..100, page_size 1..50;
   no full traversal or unbounded access. Check highest member points with points
   desc/page 1 and lowest Gomoku points with total_score asc/page 1. Current facts
   must call tools even if older history/summary already answers the question.
   Source cards should show localized ordering/page, returned count and a more
   results hint, without claiming global rank. Query rows/filters stay in bounded
   model evidence, never source headers. Unspecified normal versus AI boards and
   duplicate member names require clarification; exact names must be explicit,
   never query phrases or guessed classes. No admin records or business writes
   are available, even to administrators using the AI. Tool planning keeps the UI
   generating; normalized final-answer SSE is sent after the final turn is collected.
   Check formulas in both Chat and the assistant; code/currency stay literal.
   Real generation uses shared quota and provider billing; local mock validation
   does not establish deployed endpoint permissions or live model behavior.
   Deployment and live publication remain separate administrator actions.

All management uses assistant_admin_* through the existing authenticated Chat edge
function. Super-admin authorization and optimistic version checks stay authoritative
on the server. No seed upload, publication, upstream call or deployment runs automatically.
