# 算法社下一个项目 · 提案征集（2026-10）

> 背景：现有网站已经跑通一整套基础设施。新项目不重建地基，只在其上长出新东西。
> 本文用于向社员征集意见，请在第 6 节投票表打分。

---

## 1. 先划清边界：现有资源能做什么、不能做什么

**手上有的**

| 资源 | 能提供什么 |
| --- | --- |
| GitHub Pages | 纯静态托管，可放任意 HTML/JS/CSS/WASM，无限流量，但不能跑服务端代码 |
| Supabase 免费版 | Postgres 数据库、Auth 账号体系、Storage 文件存储、Edge Functions（短时无状态函数）、Realtime 推送 |
| AIHarness | 本地/API 方式的大模型调用能力，可做批处理、离线生成、内容生产 |
| 已建成的站内设施 | 登录/权限/超管、积分与商城、通知中心、活动与报名、社团盘、小Bru 助手与配额、四个游戏排行榜、七个算法可视化实验室 |

**明确做不到的**（会直接淘汰一些听起来很酷的想法）

- 无法跑常驻服务进程：没有排队机、不能长时间跑编译、不能开长连接服务器。
- Supabase Edge Function 有硬上限：**CPU 时间 2 秒、内存 256MB、免费版墙钟 150 秒**。它适合"轻校验 + 记账"，不能当判题机或编译器。
- **GitHub Actions 分钟数对公开仓库免费，但服务条款禁止把它当作 serverless 应用按请求触发**。它只能用于这个仓库自身的构建与测试，不能拿来做在线判题后端。
- 免费额度的数据库/存储/函数调用是有限的，涉及大量文件或高频轮询的设计要提前算账。
- 不能接入付费第三方服务（在线判题 SaaS、付费图床、付费短信等）。

**所以好项目的形状是**：计算放在浏览器（Web Worker / WASM）或社团自己的一台电脑上，数据落在 Supabase，服务端只做"轻校验 + 记账"，内容生产可以用 AIHarness 离线批量做。凡是"提交即触发云端执行"的设计，先确认它没有踩到上面两条。

## 2. 提案 A：算法策略竞技场（Bot Arena）　→ 一句话：让每个社员写一段 JS 策略，放进擂台互相对打

**做什么**
把五子棋那套"两个引擎换色对局 + 棋谱重放 + 指纹校验 + 排行榜"抽成通用擂台。社员提交一个 `strategy.js`（输入局面，输出落子/动作），系统自动安排它和其他策略打若干局，出 ELO 排名、对局回放、胜率矩阵。首发可做三个题目：五子棋、贪吃蛇对撞、俄罗斯方块竞速。

**为什么适合现有资源**
这是复用度最高的方案。仓库里最难的部分——Worker 隔离运行不可信代码、对局合法性校验、结果指纹、换色双边验收、排行榜 RPC——五子棋项目已经全部做完并踩过坑。新项目主要是"把专用代码参数化"，而不是从零造。

**主要新增工作**
- 通用的 `strategy` 接口与 Worker 沙箱（限时、限内存、禁止网络）。
- 通用赛制与积分（改为 ELO/瑞士轮，替换现有的固定分数）。
- 提交管理页：上传、版本、回放、错误日志。
- 前端：擂台页 + 排名页 + 单局回放器。

**免费额度对照**：对局在浏览器里跑，几乎不消耗 Supabase；只存元数据和对局结果，几百 KB 级别。**低风险。**

**风险**
- 社员代码质量参差，沙箱必须默认"崩溃即判负"而不是拖垮页面。
- 需要设计好"如何让一个不会写 AI 的人也能 20 行代码参赛"——这是成败关键。

**社员参与方式**：写策略、做题目、当裁判设计赛制、做可视化回放。门槛低、参与面最广。

**MVP 三步**：①五子棋策略接口 + 沙箱 → ②自动对局与 ELO + 排行榜 → ③回放页与赛季。

## 3. 提案 B：算法题库 + 周赛（轻量 OJ）　→ 一句话：社内出题、线上提交、实时榜

**先说清楚：OJ 一定要有机器跑代码，问题只是这台机器是谁的**

我上一版说"判题在浏览器完成，不占服务端算力"，容易被读成"OJ 不需要算力"。这是错的。任何 OJ 的核心都是"执行别人提交的代码"，必须有一台机器真的跑它。区别只在于那台机器是云厂商的、GitHub 的、还是你自己的一台电脑。下面是核实过的四个选项。

| 执行位置 | 能跑什么 | 成本 | 致命限制 |
| --- | --- | --- | --- |
| 浏览器（Web Worker + Pyodide/WASM） | JS、Python | 0（用社员的 CPU） | 隐藏用例必须发到客户端，理论上可作弊 |
| Supabase Edge Function | 只能做极轻校验 | 免费额度内 | **CPU 时间上限 2 秒**、内存 256MB、免费版墙钟 150 秒。跑不了编译，也跑不了像样的评测 |
| GitHub Actions | C++/Python/任意语言，Ubuntu 环境 | 公开仓库**分钟数免费不限**，单 job 最长 6 小时 | **服务条款禁止**把 Actions 当作 serverless 应用的一部分按请求触发（见下） |
| 社团自己的一台电脑（自托管 runner / 判题守护进程） | 任意语言，完整工具链 | 0（机器已有） | 需要这台机器在线，且有人维护 |

**GitHub Actions 这条路为什么不能按"每提交一次就触发一次"来做**

GitHub 的附加产品条款明确禁止：

> "don't use Actions as a content delivery network or as part of a serverless application"
> "If using GitHub-hosted runners, any other activity unrelated to the production, testing, deployment, or publication of the software project associated with the repository"

按提交实时触发判题，正好落在"把 Actions 当作 serverless 应用的一部分"这一条上。**不要这么设计**，账号被封的代价远大于省下的钱。Actions 可以合法承担的是"对这个仓库自身代码的测试"——例如每晚批量重判已入库的题解、校验题目数据文件格式。这类用法是灰白区里的白，但也不能拿它当在线判题后端。

**所以 B 的现实做法是分阶段，按"要不要支持 C++"决定架构**

*阶段一（零成本，可立刻做）*：只支持 JS 和 Python，判题在浏览器 Worker 里跑。用 Pyodide 加载 Python 解释器（约 10MB，首次加载后缓存）。隐藏用例确实是下发到客户端的，接受这个妥协，配套缓解：用例分片下发、顺序随机化、只回传通过/失败不回传用例内容、赛后对异常快的通过做人工抽查。社内教学场景下这个妥协是合理的。

*阶段二（要 C++ 时）*：在社团活动室放一台常开的电脑，跑一个自托管判题守护进程。流程是：前端把代码写进 Supabase 的 `submissions` 表并置为 pending → 那台机器轮询取任务 → 本地编译运行、套用时间/内存限制 → 把结果写回表 → 前端轮询或走 Realtime 拿结果。这台机器是你已经有的资源，完全合法，而且能跑真正的 C++。代价是它必须开着，且需要一个沙箱（Windows 上可用 Job Object 限制内存/CPU，或直接用 Docker）。

*如果想彻底绕开"执行代码"*：可以做**输出型题目**（提交答案/输出文件而不是代码），用 Edge Function 比对存储的答案即可，2 秒 CPU 完全够用，且无法作弊。缺点是考不出编程能力，只适合作为题库里的一小类。

**这套设计里 Supabase 干什么**
题库、提交记录、榜单、周赛状态都是普通表。真正需要算力的部分全部外包给浏览器或社团那台电脑，Supabase 只做"存代码 + 存结果 + 算排名"，这是它擅长的。

**其余可复用的**
已有的积分、通知、活动报名、权限体系可以直接接上：做完题加分、周赛发通知、报名走活动模块。

**风险（要说清楚）**
- 浏览器判题意味着隐藏测试用例最终是"发到客户端"的，理论上可以作弊。对社团内部教学场景可接受，缓解手段：用例分片下发、随机顺序、结果不回传用例原文、赛后人工抽查。
- 一旦要支持 C++，就必须有一台常开机器，这是运维成本而非开发成本，最容易在学期中悄悄停摆。
- **不要**用 GitHub Actions 按提交触发判题，违反服务条款。
- C++ 无法在浏览器里评测，只能"提交代码 + 人工/离线评测"，会破坏体验一致性。建议一期明确只支持 JS/Python。
- 出题是本方案真正的成本：需要 2–3 名社员持续供题，否则会空转。

**社员参与方式**：出题、写题解、当出题组、组织周赛、维护评测器。

**MVP 三步**：①JS/Python 浏览器判题 + 提交记录 → ②个人进度与周赛模式（含封榜）→ ③若确定要 C++，再搭社团自托管判题机。

**运维提醒**：阶段一的判题完全在浏览器里，没有运维负担；阶段二引入常开机器后，需要指定一位社员负责"机器在线、磁盘不爆、沙箱规则更新"。这项人力如果凑不齐，就停在阶段一。

## 4. 提案 C：AI 讲题教练 + 个人错题本　→ 一句话：做错一题，AI 沿着你的代码讲到会

**做什么**
在现有小Bru 助手之上做一个"学习闭环"：社员提交一次解法（或贴出错因），AI 先定位卡点，再给分层提示（只给方向 → 给关键步骤 → 给完整讲解），最后自动生成 2 道同类型变式题，进入个人错题本，按间隔重复推送复习。

**为什么适合现有资源**
- 站内已有 AI 聊天基础设施：模型代理、配额与租约、会话归档、管理后台。这套是整个网站最值钱的部分之一，但现在的定位是"通用聊天"，没有落进具体学习场景。
- 错题本、复习提醒都可以用现有表 + 通知中心实现，不需要新服务。
- 讲解内容可以用 AIHarness 离线批量生成并审校后入库，避免每次现算、控制免费额度消耗。

**主要新增工作**：结构化"题目-尝试-错因-变式"数据模型；分层提示的提示词与内容库；复习调度；错题本页面。

**免费额度对照**：中度风险。若每次都用在线模型现算，会吃掉聊天配额；对策是"离线生成讲解、在线只做个性化点评"，并复用现有配额与黑名单机制。

**风险**
- 内容质量依赖提示词与审校，容易讲得"像模像样但错"。
- 如果没有配套题库（提案 B），错题本就缺输入，两个方案天然配套。

**社员参与方式**：审校 AI 讲解、标注错因、写变式题、设计复习策略。

**MVP 三步**：①单题分层提示 → ②错题本存档与复习提醒 → ③变式题自动生成与人工审校。

## 5. 提案 D：算法训练营（课程 + 作业 + 结业）　→ 一句话：把两本教材变成有进度、有作业、有证书的课程

**做什么**
基于已有 Python / C++ 教材 PDF，做章节化的学习路径：每章有导读、配套实验（直接链到现有七个可视化实验室）、作业提交、自动评分（客观题 + 代码片段）、进度与结业证明。适合新生入门和老生带教。

**为什么适合现有资源**
教材、资源中心、可视化实验室都已存在，缺的只是"把它们串成一条有节奏的线"。数据模型简单，全部落在 Supabase；作业评分用浏览器判题或客观题即可。

**免费额度对照**：低风险。

**风险**
- 这是"内容项目"而不是"工程项目"，工程量小但人力投入大，最容易做成一个空壳页面。
- 需要有人持续维护教学节奏（每周发课、批作业），否则会烂尾。

**社员参与方式**：编讲义、出作业、带教答疑、录讲解。

**MVP 三步**：①一章完整跑通（导读+实验+作业+评分）→ ②进度页与结业 → ③扩到第二本教材。

| B 题库 + 周赛 | 很高（直接对应训练） | 中高（积分/通知/活动可复用） | 中高 | 低（但 C++ 需要一台常开机器） | 高 | 中（出题压力 + 运维） | |

| D 训练营课程 | 中高（对新生最友好） | 高（教材/实验室已存在） | 低 | 低 | 中 | 高（靠人维护） | |

**我的建议**

1. 若只能选一个：**A**。它把仓库里最难、最不可替代的能力（沙箱、对局校验、排名）复用到底，且"写一段 JS 就能参赛"的门槛能带来最广的参与面。
2. 若社团当前的主要诉求是"提高做题/竞赛水平"：**B**，并且把 **C** 作为它的第二阶段（先有题库，错题本才有意义）。
3. **D** 不建议单独立项。它应该作为 A 或 B 的"新手入口"存在——先有一条引导线，不必先建一座课程大楼。
4. B + C 是一组天然搭档，A 是唯一能独立成立的单体项目。

**投票时请一并回答两个问题**

- 你每周大概能投入多少时间？（<2h / 2–5h / >5h）
- 你更想"用"这个项目，还是"做"这个项目？（这决定了我们优先做能用的还是能做深的）

**淘汰掉的候选（供参考，避免重复讨论）**

- 在线协作文档/笔记：与社团盘、资源中心重叠。
- 爬虫/数据抓取平台：违反静态托管与免费额度前提。
- 通用论坛/社区：与现有消息、通知、活动模块重叠，且没有算法特色。
- 视频课程/直播：需要付费存储与带宽，超出免费额度。
- **用 GitHub Actions 按提交触发判题**：技术上免费且能跑 C++，但服务条款明确禁止把 Actions 当作 serverless 应用的一部分按请求触发，有封号风险。想支持 C++ 就走社团自托管机器。

## 7. 无论选哪个，都遵守的既有约定

- 新页面接入 `club-ui.css` + `club-shell.js`，不另立一套视觉；暗色为默认，亮色必须单独覆盖。
- 动态文案统一走 `refreshXxx()` + `club:langchange`，不写死中文。
- 新增表结构与函数进 `supabase/*.sql` 主脚本，交付前跑 `check-gomoku-sql-syntax.mjs` 级别的真实语法校验。
- 涉及 AI 的功能必须复用现有配额、租约和归档机制，不新开一条不受控的调用链。
- 提交前跑 `check-ui-tokens.mjs` 与 `version-static-assets.mjs`，保持资产版本一致。
