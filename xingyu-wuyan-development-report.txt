《行于无垠》横版动作闯关与实时对战项目
开发日志 Report

项目名称：行于无垠
项目类型：HTML5 横版动作闯关射击游戏、实时联机 PK 游戏
项目状态：持续开发与优化中
主要技术：HTML5、JavaScript、Phaser 3、Supabase、PostgreSQL、Supabase Edge Functions、Broadcast、Presence、Postgres Changes
项目部署形式：静态网页部署，可发布至 GitHub Pages 等静态托管平台

一、项目概述

《行于无垠》是我为算法社设计和开发的一款横版像素风动作游戏。项目最初是一个简单的 Phaser 3 闯关原型，后来逐步扩展为包含多关卡、Boss、角色养成、无尽模式、实时联机 PK、公告系统、管理员系统和 Supabase 数据存档的完整网页游戏项目。

游戏采用横向卷轴结构。玩家可以左右移动、跳跃、瞄准、持续射击、切换武器、使用闪身和特殊技能，并在关卡中与不同类型的敌人战斗。玩家需要击败关卡内全部敌人后才能触碰终点旗帜通关。金币、生命豆、能量豆和技能豆用于构建局内资源循环，通关奖励和养成系统构成长期成长目标。

这个项目的核心目标不是只制作一个可以运行的小游戏，而是尝试将算法社的技术特色转化为可交互的作品，综合实践游戏逻辑、实时通信、数据持久化、权限控制、前端交互和系统调试。

二、项目发展过程

阶段一：原型验证

项目最初使用 Phaser 3 构建最小可玩原型，实现了主角移动、跳跃、平台碰撞、敌人、金币、能量豆、技能豆、生命豆和终点旗帜。

早期原型采用较短的单方向卷轴关卡，用于验证以下基础问题：

1. Phaser 场景是否能够在静态网页环境中正常启动。
2. 主角能否在平台上稳定移动和跳跃。
3. 子弹、敌人和平台之间的碰撞是否可靠。
4. 关卡完成后能否解锁下一关。
5. 游戏素材能否从本地和 GitHub Pages 路径正确加载。

在这一阶段发现并修复了多个基础问题，包括关卡高度设计不合理、终点旗帜无法触发、玩家穿墙、玩家脚部与平台位置不一致，以及本地文件打开时资源路径异常等问题。

阶段二：角色素材与战斗系统

项目随后加入了主角、敌人和武器的像素素材。主角支持站立、移动和跳跃三种状态，并根据左右方向切换贴图。敌人分为三种：

1. 黄色敌人：移动速度快、生命值较低、接触伤害高。
2. 绿色敌人：移动速度较慢、生命值较高、能够发射绿色子弹。
3. 粉紫色敌人：能够在空中飞行、生命值较高、能够发射红色子弹。

远程武器逐步扩展为手枪、霰弹枪、冲锋枪、激光枪和狙击枪。项目还加入了匕首和长刀两种近战武器。武器模型会贴近角色手部，并跟随瞄准方向旋转。针对图片体积过大和新用户加载慢的问题，项目增加了图片压缩和 optimized 资源目录，减少 Phaser 初始化时需要读取的数据量。

阶段三：养成系统

为了让游戏具有长期目标，我设计了多条独立的养成路线：

1. 生命强化：提升生命值，并在高等级解锁生命恢复和紧急恢复能力。
2. 攻击强化：提升枪械和近战基础攻击力。
3. 射击强化：降低射击间隔，解锁二连发、三连发、穿透和武器能力。
4. 身法：解锁闪身、追踪闪身、空袭、二段跳、浮空和暗杀令。
5. 近战强化：提升匕首和长刀伤害、攻击范围、减伤和生命恢复能力。
6. 弹药强化：增加枪械伤害、爆裂弹、元素附魔、矢量弹道和超载开火等效果。
7. 装甲强化：增加装甲、能量护盾、减伤、反伤和装甲恢复能力。
8. 作战狂人：同时强化生命、枪械、近战、装甲和护盾。
9. 生命进化、攻击进化和装甲进化：提供高等级成长和阶段性属性跃迁。
10. 战神与战神 II：作为后期无上限或高上限的综合成长体系。

这些系统让我实际处理了大量属性计算、前置条件、等级上限、百分比叠加、技能解锁、冷却时间和局内状态同步问题。为避免养成说明遮挡游戏界面，我还设计了独立的养成说明界面和翻页式内容展示。

阶段四：关卡与 Boss 设计

关卡数量从最初的三个测试关卡扩展到 150 个以上。常规关卡按照长度、敌人数量、层数和道具数量逐步增加难度；部分关卡被设计为 Boss 关卡。

关卡设计重点包括：

1. 关卡长度从教学关的 3000 左右扩展到后期的数万单位。
2. 浮空平台高度控制在 2 到 4 层，并检查玩家是否能够合法到达道具和敌人位置。
3. 常规关卡设置金币、生命豆、技能豆和能量豆，形成资源管理和探索动力。
4. Boss 关卡采用不同弹幕机制，包括扇形散射、追踪弹、地面波、激光扫射、弹幕环和扩散弹幕。
5. Boss 具有多阶段行为，随着生命值下降改变攻击频率、移动方式和弹幕组合。
6. 关卡必须击败全部敌人后才能触碰旗帜通关。
7. 无尽模式每隔固定时间刷新敌人波次，并按照波次提高敌人属性。

Boss 设计过程中，我尝试把不同养成路线与不同机制对应起来。例如，地面波考验跳跃时机，激光扫射考验闪身，追踪弹要求持续移动，弹幕环则考验火力和穿透能力。这使关卡不只是单纯增加敌人数量，而是要求玩家根据机制调整玩法。

阶段五：数据存档与 Supabase

项目使用 Supabase 保存账号、金币、养成等级、关卡进度和最高分。数据库主要包含游戏用户表、关卡进度表、事件领取记录、联机房间、对战成员和排行榜视图。

数据库函数负责处理：

1. 游戏账号注册、登录和会话令牌。
2. 养成数据保存与读取。
3. 关卡最高分记录。
4. 首次通关奖励和重复挑战奖励。
5. 活动奖励的单次领取限制。
6. 联机 PK 房间、押注和结算。
7. 游戏服务开关。
8. 公告附件的单账号单附件领取。

在 SQL 开发过程中，我多次处理了 PostgreSQL 函数签名、RETURNS TABLE、变量命名冲突、ON CONFLICT 更新和重复领取等问题。为了防止客户端直接伪造数据，关键奖励和金币变更尽量放在数据库函数中执行，而不是只依赖浏览器端逻辑。

三、实时联机 PK 系统

联机 PK 是项目后期的重要扩展。设计目标是让双方在长度约 1500 的竞技场中使用与单机闯关相同的角色、武器、移动和技能体验。

实时通信部分采用 Supabase 的多种能力：

1. Broadcast：同步角色位置、瞄准方向、射击事件、技能事件和击退事件。
2. Presence：显示房间内在线成员和连接状态。
3. Postgres：保存房间状态、押注、胜负和结算结果。
4. Edge Function：作为部分服务端校验和联机接口入口。

联机过程中遇到的问题包括：

1. 第二场对局无法使用键盘。
2. 旧 Phaser 场景未销毁，导致输入状态和物理状态残留。
3. 对手角色贴图比例错误或浮空。
4. 对手子弹不可见或无法造成伤害。
5. 双方移动逐渐不同步。
6. 伤害事件重复或丢失。
7. 长刀击退和装甲反伤无法传递给对手。
8. 对局结束后一方停留在结算状态。

针对这些问题，我增加了状态包序号、命中事件 ID、远端子弹 ID、状态去重、旧场景销毁、输入焦点恢复、对手物理碰撞箱、远端击退事件和结果提交保护。联机 PK 的代码最终复用了单机 Game 场景的移动、跳跃、射击、近战、护甲和技能计算，避免为 PK 单独制作一套不一致的战斗逻辑。

四、移动端和响应式适配

项目同时支持电脑和手机。

电脑端支持：

1. A、D 或方向键移动。
2. W、上方向键或空格跳跃。
3. 鼠标移动瞄准。
4. 按住鼠标左键持续攻击。
5. 右键切换武器。
6. X、S、E、F、V、C、Z 等技能操作。

移动端支持：

1. 虚拟摇杆左右移动。
2. 滑动屏幕瞄准。
3. 按住攻击按钮持续开火。
4. 跳跃、闪身、空袭、大招、武器切换和模式切换按钮。

我根据不同屏幕比例调整了画布、控制区、按钮网格和横屏布局，避免手机上游戏区域与操作按钮同时显示不完整。

五、管理员与公告系统

项目新增了游戏服务管理和公告系统。管理员可以：

1. 开启或关闭游戏服务。
2. 在维护期间显示“服务器升级维护中，请稍后再试”。
3. 查看所有已注册游戏账号。
4. 修改指定玩家的金币数量。
5. 创建、编辑、发布和删除游戏公告。
6. 为公告添加多个金币附件。
7. 确保每个账号对每个附件只能领取一次。

管理员权限不再只依赖固定的 chm 账号。社团盘中被标记为超级管理员的 Supabase Auth 账号，可以自动获得游戏管理员权限。这个设计把社团整体权限系统与游戏管理系统连接起来，同时保留服务端权限校验，避免只在前端隐藏按钮。

六、主要技术问题与解决方式

1. Phaser 初始化失败

原因包括外部脚本加载失败、素材路径错误和场景 create 阶段异常。解决方式是增加初始化阶段记录、错误捕获、资源 fallback、启动 watchdog 和更清晰的错误提示。

2. 角色贴图抽搐

通过区分 standing、moving 和 jumping 状态，只有检测到实际移动时才切换行走贴图，静止时固定显示站立贴图，并统一左右朝向和碰撞箱尺寸。

3. 玩家穿墙和脚部位置异常

通过 Phaser Arcade Physics 的平台碰撞、固定尺寸物理箱、合法落脚点检查和贴图 origin 调整，解决视觉模型与物理实体不一致的问题。

4. 射击与伤害不同步

为子弹和命中事件增加唯一 ID，并通过 Broadcast 与状态包双通道同步，受击方统一调用伤害处理函数。同时加入护甲、能量护盾、反伤、击退和死亡状态的服务端事件传递。

5. 高等级状态栏溢出

将状态拆分为基础信息、战斗信息、防御信息和完整详情，并增加展开/折叠逻辑。PK 模式则将双方核心状态放在画布底部，减少顶部信息对战斗区域的遮挡。

6. 重复发放奖励

使用唯一索引和数据库冲突处理记录领取状态，保证活动奖励、公告附件和首通奖励不能通过重复登录反复领取。

七、项目成果

截至目前，项目已经具备以下功能：

1. 150 个以上的横版关卡结构。
2. 多层平台和大量不同类型敌人。
3. 多种 Boss 和弹幕机制。
4. 五种远程武器和两种近战武器。
5. 多条可组合的角色养成路线。
6. 生命、装甲和能量护盾系统。
7. 无尽模式和活动奖励。
8. 账号系统、进度存档、最高分排行榜。
9. Supabase 实时联机 PK、房间和押注结算。
10. 电脑、手机和横屏布局适配。
11. 游戏管理员、服务开关、公告和金币附件系统。
12. 本地静态部署和 GitHub Pages 部署兼容。

八、个人收获

这个项目让我从一个简单的游戏原型，逐步学习并实践了完整软件项目中的多个层面。除了编写游戏逻辑，我还处理了资源组织、响应式布局、数据库建模、RPC 函数、权限控制、实时通信、客户端状态同步、异常监控和部署兼容性问题。

其中最重要的收获是认识到，复杂系统的难点并不只在于“增加功能”，还在于保证不同功能之间的一致性。例如，单机模式和 PK 模式必须使用相同的战斗规则；浏览器端显示的金币和数据库中的金币必须保持一致；关卡解锁不能因为客户端缓存而倒退；移动端按钮和桌面端键盘也必须指向同一套游戏行为。

我还逐渐形成了分阶段开发、先验证核心循环、再扩展功能、持续记录错误阶段和保护数据一致性的开发习惯。项目中出现的许多 Bug 最终都转化成了对生命周期管理、事件去重、权限边界和状态同步的具体理解。

3. 进一步完善联机 PK 的服务端反作弊校验。
4. 增加更细致的战斗统计和对战历史。

总结

《行于无垠》从一个 Phaser 3 原型发展为一个结合游戏开发、数据库、实时通信和权限系统的综合项目。它既是一个可玩的网页游戏，也是我在算法社中将编程知识转化为实际产品的长期实践。通过这个项目，我积累了从需求设计、架构实现、Bug 定位到部署维护的完整经验，并进一步明确了自己对软件工程、交互系统和实时应用开发的兴趣。
